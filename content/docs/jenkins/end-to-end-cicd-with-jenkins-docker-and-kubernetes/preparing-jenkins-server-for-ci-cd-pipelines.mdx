Everything you learned in this bootcamp comes together in this section. We will build one pipeline that takes code from GitHub, builds it with Maven, packs it into a Docker image, pushes that image to Docker Hub, and deploys it to a Kubernetes cluster on Amazon EKS. A user then opens the application through an AWS load balancer.

Jenkins does not do any of this work by itself. It runs commands. So before we write a single line of the pipeline, the Jenkins server must have every tool those commands need. That is what this lesson is about.

![End-to-end flow: developer pushes to GitHub, Jenkins clones the code, Maven builds the WAR, Docker builds an image, the image is pushed to Docker Hub, kubectl applies manifests to Amazon EKS, a LoadBalancer Service exposes the pods to the user](https://dyz1pdcuffwr5.cloudfront.net/Jenkins/cicd-complete-pipeline.svg)

## What each tool does in the pipeline

| Tool | Stage of the pipeline | Already on the server? |
| --- | --- | --- |
| **Git** | Clone the project from GitHub | Yes, Ubuntu ships with it and the Git plugin uses it |
| **Maven** | Compile, test and package the WAR file | Yes, registered as the `maven` tool in [Building Your First Java Application with Jenkins](/docs/jenkins/freestyle-jobs/building-your-first-java-application-with-jenkins) |
| **Docker** | Build the image and push it to Docker Hub | No, install it now |
| **kubectl** | Send Deployment and Service manifests to the cluster | No, install it now |
| **AWS CLI** | Give kubectl a login token for EKS (`aws eks get-token`) | No, install it now |
| **Docker Hub account** | Store the images | Create one at hub.docker.com if you do not have it |
| **EKS cluster** | Run the containers | Created in the next two lessons |

You do not need `eksctl` on the Jenkins server. eksctl creates and deletes clusters, and that is an admin task we do from a separate machine (the EKS home server in the next lesson). The pipeline only deploys into a cluster that already exists, and for that kubectl plus the AWS CLI are enough.

![Two EC2 instances: the Jenkins server with Java, Jenkins, Git, Maven, Docker, kubectl and AWS CLI, and the EKS home server with AWS CLI, eksctl and kubectl. Both use the same IAM role. The EKS home server creates the cluster, the Jenkins server deploys to it](https://dyz1pdcuffwr5.cloudfront.net/Jenkins/cicd-servers-and-tools.svg)

## Before you start: check the server size

Docker images are large. The image we build in this section is about 650 MB on disk, and every build adds another one. On the default 8 GiB root volume the disk fills up after a handful of builds, and Jenkins starts failing with "no space left on device".

```bash
df -h /
free -h
```

For this project use at least **20 GiB** of disk and **4 GiB** of memory (the `c7i-flex.large` from [Jenkins Installation and Initial Setup](/docs/jenkins/jenkins-setup/jenkins-installation-and-initial-setup) is fine). If your root volume is small, increase it in the EC2 console under **Elastic Block Store > Volumes > Modify volume**, then grow the partition and file system on the server:

```bash
sudo growpart /dev/nvme0n1 1     # grow partition 1 to fill the bigger volume
sudo resize2fs /dev/nvme0n1p1    # grow the ext4 file system
df -h /
```

Run `lsblk` first and use the device name it shows. [EBS Basics and Root Volume](/docs/aws/compute-with-ec2/ebs-basics-and-root-volume) explains volumes in more detail.

## Step 1: install kubectl

SSH into the Jenkins server as `ubuntu`. The video uses commands generated by an AI assistant, and they match the [official Kubernetes instructions](https://kubernetes.io/docs/tasks/tools/install-kubectl-linux/). Here is the same thing with the checksum check the official page recommends:

```bash
cd /tmp
KVER=$(curl -L -s https://dl.k8s.io/release/stable.txt)
curl -LO "https://dl.k8s.io/release/${KVER}/bin/linux/amd64/kubectl"
curl -LO "https://dl.k8s.io/release/${KVER}/bin/linux/amd64/kubectl.sha256"
echo "$(cat kubectl.sha256)  kubectl" | sha256sum --check
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
rm -f kubectl kubectl.sha256
kubectl version --client
```

| Part | Meaning |
| --- | --- |
| `stable.txt` | Returns the newest stable Kubernetes version, for example `v1.37.1` |
| `sha256sum --check` | Confirms the file was not corrupted during download. It must print `kubectl: OK` |
| `install -m 0755 ... /usr/local/bin/kubectl` | Copies the binary into a folder that is on every user's `PATH`, including the `jenkins` user |

Installing into `/usr/local/bin` matters here. If you install a tool into `~/bin` of the `ubuntu` user, you can run it, but Jenkins cannot, because Jenkins runs every build as the separate Linux user `jenkins`.

## Step 2: install the AWS CLI v2

```bash
sudo apt update
sudo apt install -y unzip curl
cd /tmp
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip -q -o awscliv2.zip
sudo ./aws/install --update
rm -rf aws awscliv2.zip
aws --version
```

The installer puts `aws` in `/usr/local/bin`, so the `jenkins` user can run it too. Do **not** run `aws configure` with access keys on this server. In [Configuring Jenkins to Connect with Amazon EKS](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/configuring-jenkins-to-connect-with-amazon-eks) we attach an IAM role to the instance instead, so no secret is stored on disk.

<Callout type="info" title="Use the AWS installer, not apt">
Ubuntu's `awscli` package is often far behind and may even be version 1. EKS needs AWS CLI 2.12.3 or later for `aws eks get-token` to work with current clusters. The official zip installer always gives you the latest v2.
</Callout>

## Step 3: install Docker and let Jenkins use it

This is the script shown in the video, updated to the current [Docker Engine install guide for Ubuntu](https://docs.docker.com/engine/install/ubuntu/). Save it as `install-docker.sh`, then run `chmod +x install-docker.sh && ./install-docker.sh`.

```bash title="install-docker.sh"
#!/usr/bin/env bash
set -euo pipefail

# Docker's official GPG key
sudo apt update
sudo apt install -y ca-certificates curl
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# Docker apt repository
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF

# Install Docker Engine, CLI, containerd and the buildx/compose plugins
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# Start Docker now and on every boot
sudo systemctl enable --now docker

# Allow the jenkins user to talk to the Docker daemon
sudo usermod -aG docker jenkins

# Jenkins must restart to pick up the new group
sudo systemctl restart jenkins

docker --version
```

The two lines at the end are the ones that matter most for CI/CD:

| Command | Why |
| --- | --- |
| `usermod -aG docker jenkins` | The Docker daemon listens on the socket `/var/run/docker.sock`, which only `root` and members of the `docker` group can use. Without this line every `docker build` in a pipeline fails with `permission denied while trying to connect to the Docker daemon socket` |
| `systemctl restart jenkins` | Group membership is read when a process starts. The running Jenkins process does not see the new group until it restarts |

The video's generated script used an older style (`docker.gpg` key and a one-line `docker.list` file). It still works, but Docker's documentation now uses the `docker.asc` key and a `docker.sources` file, as above. Both install the same packages.

<Callout type="warn" title="The docker group is as powerful as root">
Anyone in the `docker` group can start a container that mounts the host's root file system, which is the same as having root on the server. That is acceptable on a dedicated Jenkins server for learning. In a company, protect who can create and edit pipelines, or build images on separate agents. We covered agents in [Jenkins Master Agent Architecture Introduction](/docs/jenkins/security-and-distributed-builds/jenkins-master-agent-architecture-introduction).
</Callout>

After the restart, refresh Jenkins in the browser and log in again if it asks.

## Step 4: verify as the jenkins user

Checking as `ubuntu` is not enough. What matters is what the `jenkins` user sees, because that is the user every pipeline runs as.

```bash
sudo -u jenkins kubectl version --client
sudo -u jenkins aws --version
sudo -u jenkins docker run --rm hello-world
id jenkins
```

The last command should list `docker` among the groups:

```text
uid=111(jenkins) gid=113(jenkins) groups=113(jenkins),988(docker)
```

If `docker run` prints "Hello from Docker!", the Jenkins server is ready for Docker builds. You can also confirm it from Jenkins itself with a tiny pipeline:

```groovy title="Pipeline script (tool check)"
pipeline {
    agent any
    stages {
        stage('Tool check') {
            steps {
                sh 'whoami'
                sh 'docker version'
                sh 'kubectl version --client'
                sh 'aws --version'
            }
        }
    }
}
```

`whoami` prints `jenkins`, which proves the point about the build user.

<Callout type="info" title="About the kernel upgrade message">
While installing packages, Ubuntu may print "Pending kernel upgrade" and suggest a reboot. The tools work without it, but rebooting the instance at a quiet moment (`sudo reboot`) applies security updates. Jenkins and Docker start automatically after the reboot because both are enabled with systemd.
</Callout>

## What comes next

The Jenkins server can now build and push images. To deploy, it also needs a cluster and permission to use it:

1. Create a machine with eksctl and use it to create the EKS cluster (next two lessons).
2. Give the Jenkins server a kubeconfig and an IAM identity the cluster trusts.
3. Write the pipelines.

If you already created the cluster in the Kubernetes course, you can skim the next two lessons and go straight to [Configuring Jenkins to Connect with Amazon EKS](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/configuring-jenkins-to-connect-with-amazon-eks).

## Common errors

<Accordions>
<Accordion title="permission denied while trying to connect to the Docker daemon socket">
The `jenkins` user is not in the `docker` group, or Jenkins was not restarted after you added it. Run `id jenkins`, then `sudo systemctl restart jenkins`.
</Accordion>
<Accordion title="kubectl: not found (only inside Jenkins)">
You installed kubectl somewhere that is not on the `jenkins` user's `PATH`, for example `/home/ubuntu/bin`. Install it to `/usr/local/bin` as shown above.
</Accordion>
<Accordion title="unzip: command not found">
Fresh Ubuntu images do not include `unzip`. Install it with `sudo apt install -y unzip` before running the AWS CLI installer.
</Accordion>
<Accordion title="no space left on device during docker build">
The root volume is full of images and build workspaces. Run `docker system df` to see usage, `docker image prune -a` to remove unused images, and increase the EBS volume.
</Accordion>
</Accordions>

## Try It Yourself

1. Install kubectl, the AWS CLI and Docker on your Jenkins server and record the three versions.
2. Run `sudo -u jenkins docker ps` before and after `usermod`, and before and after restarting Jenkins. Note exactly when it starts working.
3. Create the "Tool check" pipeline above and confirm `whoami` prints `jenkins`.
4. Run `df -h /` and `docker system df`, and decide whether your disk is big enough for 10 builds of a 650 MB image.
