The image is on Docker Hub. Nobody can use it yet. The last step is to tell Kubernetes: "run two copies of this image and give users a way to reach them". In Kubernetes you say that with YAML manifests, and Jenkins sends them to the cluster with `kubectl apply`.

By the end of this lesson, one click on **Build Now** takes the code from GitHub all the way to a URL you can open in the browser.

![EKS_Deploy](https://dyz1pdcuffwr5.cloudfront.net/Jenkins/cicd-eks-deploy.svg)

## Step 1: make sure Jenkins is allowed into the cluster

The lecture starts by giving the Jenkins IAM role an EKS access entry with cluster admin rights. Whether you need this depends on how your cluster was created, so check first. On the EKS home server:

```bash
aws eks describe-cluster --name telusko-learning --region ap-south-1 \
  --query 'cluster.accessConfig.authenticationMode' --output text

aws eks list-access-entries --cluster-name telusko-learning --region ap-south-1
```

- If the mode is `API` or `API_AND_CONFIG_MAP` (eksctl's default) **and** the list already contains `arn:aws:iam::<account-id>:role/eks-telusko-learning`, you are done. That entry was created automatically for the identity that created the cluster, and the Jenkins server uses the same role.
- If the role is **not** in the list (for example, you created the cluster with an IAM user, or Jenkins uses its own role), create the entry and give it permissions, exactly as in the video:

```bash
aws eks create-access-entry \
  --cluster-name telusko-learning \
  --principal-arn arn:aws:iam::<account-id>:role/eks-telusko-learning \
  --region ap-south-1

aws eks associate-access-policy \
  --cluster-name telusko-learning \
  --principal-arn arn:aws:iam::<account-id>:role/eks-telusko-learning \
  --policy-arn arn:aws:eks::aws:cluster-access-policy/AmazonEKSClusterAdminPolicy \
  --access-scope type=cluster \
  --region ap-south-1
```

If the role already has an entry, the first command fails with `ResourceInUseException`. That is harmless and means the entry exists. Find your account ID with `aws sts get-caller-identity --query Account --output text`, and never paste it into public screenshots or forums.

`AmazonEKSClusterAdminPolicy` with `type=cluster` gives full control of the whole cluster, which is fine for a practice cluster. For a real Jenkins identity, use `AmazonEKSEditPolicy` scoped to the namespaces it deploys to, as shown in [Configuring Jenkins to Connect with Amazon EKS](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/configuring-jenkins-to-connect-with-amazon-eks).

## Step 2: free some disk on the Jenkins server

The previous pipeline left images behind. The lecture clears them before continuing:

```bash
sudo docker system prune -a
```

Type `y` to confirm. This deletes every image not used by a running container, which is fine on a practice server. Do not run it on a shared build server where other jobs rely on cached images.

## Step 3: add the Deploy to Kubernetes stage

The lecture renames the `pipeline-docker` job to `complete-cicd-pipeline` (job page > **Rename**) and adds one more stage. The stage writes two YAML files and applies them.

Here is the full pipeline, building on the version from the [previous lesson](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/build-and-push-docker-images-using-jenkins-pipeline):

```groovy title="Pipeline script (complete-cicd-pipeline)"
pipeline {
    agent any

    environment {
        DOCKERHUB_USER = 'your-dockerhub-username'
        IMAGE_NAME     = "${DOCKERHUB_USER}/my-web-app-telusko"
        IMAGE_TAG      = "${BUILD_NUMBER}"
    }

    tools {
        maven 'maven'
    }

    stages {
        stage('git clone') {
            steps {
                git branch: 'main', url: 'https://github.com/Haider7214/webapp.git'
            }
        }

        stage('maven build') {
            steps {
                sh 'mvn clean package'
            }
        }

        stage('Build Docker Image') {
            steps {
                writeFile file: 'Dockerfile', text: '''
FROM tomcat:10.1-jdk17-temurin
LABEL maintainer="Telusko"
EXPOSE 8080
COPY target/web-app-0.0.1-SNAPSHOT.war /usr/local/tomcat/webapps/ROOT.war
'''
                sh 'docker build -t $IMAGE_NAME:$IMAGE_TAG -t $IMAGE_NAME:latest .'
            }
        }

        stage('Docker Push') {
            steps {
                withCredentials([usernamePassword(credentialsId: 'dockerhub-creds',
                                                  usernameVariable: 'DOCKER_USER',
                                                  passwordVariable: 'DOCKER_PASS')]) {
                    sh '''
                        echo "$DOCKER_PASS" | docker login -u "$DOCKER_USER" --password-stdin
                        docker push $IMAGE_NAME:$IMAGE_TAG
                        docker push $IMAGE_NAME:latest
                    '''
                }
            }
        }

        stage('Deploy to Kubernetes') {
            steps {
                // Kubernetes Deployment: two copies of the app
                writeFile file: 'deployment.yaml', text: """
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web-app-deployment
spec:
  replicas: 2
  selector:
    matchLabels:
      app: web-app
  template:
    metadata:
      labels:
        app: web-app
    spec:
      containers:
      - name: web-container
        image: ${IMAGE_NAME}:${IMAGE_TAG}
        ports:
        - containerPort: 8080
"""
                // Kubernetes Service: an AWS load balancer in front of the pods
                writeFile file: 'service.yaml', text: '''
apiVersion: v1
kind: Service
metadata:
  name: web-app-service
spec:
  type: LoadBalancer
  selector:
    app: web-app
  ports:
  - protocol: TCP
    port: 80
    targetPort: 8080
'''
                sh 'kubectl apply -f deployment.yaml'
                sh 'kubectl apply -f service.yaml'
                sh 'kubectl rollout status deployment/web-app-deployment --timeout=180s'
            }
        }
    }

    post {
        always {
            sh 'docker logout || true'
            sh 'docker rmi $IMAGE_NAME:$IMAGE_TAG $IMAGE_NAME:latest || true'
        }
    }
}
```

## Reading the manifests

| Field | Meaning |
| --- | --- |
| `kind: Deployment`, `replicas: 2` | Keep two pods running at all times. If one crashes or its node dies, Kubernetes starts a replacement |
| `selector.matchLabels` and `template.metadata.labels` | Both say `app: web-app`. That is how the Deployment knows which pods belong to it. They must match |
| `image: ${IMAGE_NAME}:${IMAGE_TAG}` | The exact image this build pushed, for example `user/my-web-app-telusko:12`. The lecture used `:latest` here |
| `containerPort: 8080` | Tomcat listens on 8080 inside the container |
| `kind: Service`, `type: LoadBalancer` | Ask the cloud for an external load balancer. On EKS, AWS creates one and gives it a public DNS name |
| `selector: app: web-app` | Send traffic to every pod with this label |
| `port: 80`, `targetPort: 8080` | Users connect to port 80 on the load balancer; traffic reaches port 8080 in the pods |

The Deployment YAML uses **triple double quotes** (`"""`) so Groovy fills in `${IMAGE_NAME}` and `${IMAGE_TAG}`. That is safe here because these values are not secrets. The Service uses single quotes because it has nothing to fill in.

Why the build number in the manifest matters: `kubectl apply` only changes what is different. If the Deployment always says `:latest`, the second run of the pipeline sends an identical manifest, Kubernetes sees "unchanged", and the old pods keep running the old code even though Docker Hub has a new image. A new tag on every build changes the pod template, so Kubernetes rolls out the new version. We look at this rollout closely in the [next lesson](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/ci-cd-pipeline-with-jenkins-docker-and-kubernetes).

`kubectl rollout status` is not in the lecture. Without it, the stage turns green as soon as Kubernetes **accepts** the manifest, even if the new pods then fail to start. With it, Jenkins waits until the new pods are ready and fails the build if that does not happen within 180 seconds.

For a refresher on these objects see [Kubernetes Deployments](/docs/kubernetes/namespaces-labels-and-deployments/kubernetes-deployments-replicasets-scaling-and-self-healing) and [LoadBalancer Service Explained](/docs/kubernetes/pods-and-services/loadbalancer-service-explained).

## Step 4: run it and open the app

Click **Build Now**. The stage view gains a sixth column:

![Deploy_Stage_View](https://dyz1pdcuffwr5.cloudfront.net/Jenkins/screens/cicd-deploy-stage-view.webp)

*Build #3 ran all six stages. The older build #1 stopped at Docker Push because the deploy stage did not exist yet.*

Check the result from the EKS home server (or from the Jenkins server with `sudo -u jenkins`):

```bash
kubectl get pods
kubectl get svc
```

```text
NAME                                  READY   STATUS    RESTARTS   AGE
web-app-deployment-768f86d9c4-4n5wz   1/1     Running   0          41s
web-app-deployment-768f86d9c4-q8fqw   1/1     Running   0          41s

NAME              TYPE           CLUSTER-IP       EXTERNAL-IP                                   PORT(S)        AGE
kubernetes        ClusterIP      10.100.0.1       <none>                                        443/TCP        179m
web-app-service   LoadBalancer   10.100.238.219   a0900be...ap-south-1.elb.amazonaws.com        80:30315/TCP   47s
```

The `EXTERNAL-IP` column holds the load balancer's DNS name. You can also find it in the AWS console under **EC2 > Load Balancers**: a new load balancer of type **classic** appears, created by Kubernetes for the Service.

Open `http://<that-dns-name>` in the browser. Use `http`, not `https`. A brand new load balancer needs one to three minutes before DNS resolves and the health checks pass, so if the page does not load at first, wait and refresh.

![App_In_Browser](https://dyz1pdcuffwr5.cloudfront.net/Jenkins/screens/cicd-app-in-browser.webp)

*The application running on EKS, opened through the load balancer DNS name.*

## Hard-coding files in the pipeline

The lecture is open about this: writing the Dockerfile and the manifests inside the Jenkinsfile works, but it is not how real projects do it. The developers who own the application should own its Dockerfile and manifests, version them in Git next to the code, and review changes in pull requests. The pipeline should only run them. That is exactly what the [next lesson](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/ci-cd-pipeline-with-jenkins-docker-and-kubernetes) changes.

## Clean up

At the end of the lecture the Jenkins server is cleaned with `sudo docker system prune` and the job workspaces are wiped (job page > **Workspace > Wipe Out Current Workspace**, as in earlier lessons).

<Callout type="error" title="The load balancer costs money">
The `web-app-service` created a real AWS load balancer, billed per hour on top of the EKS cluster. When you finish practising, delete the Service **before** deleting the cluster, otherwise the load balancer can block the VPC from being deleted and keep charging you:

```bash
kubectl delete svc web-app-service
kubectl delete deployment web-app-deployment
```

Then delete the cluster as shown in [Creating Your First EKS Cluster](/docs/jenkins/end-to-end-cicd-with-jenkins-docker-and-kubernetes/creating-your-first-eks-cluster), unless you continue straight to the next lesson.
</Callout>

## Common errors

<Accordions>
<Accordion title="error: You must be logged in to the server (Unauthorized)">
Jenkins' IAM role has no access entry. Check Step 1.
</Accordion>
<Accordion title="EXTERNAL-IP stays pending">
The cloud controller could not create the load balancer. Run `kubectl describe svc web-app-service` and read the Events. Common causes are subnet tags missing on a cluster not created by eksctl, or an account limit on load balancers.
</Accordion>
<Accordion title="Pods in ImagePullBackOff">
The image name or tag is wrong, or the repository is private. Run `kubectl describe pod <name>` to see the exact image Kubernetes tried to pull, and compare it with Docker Hub.
</Accordion>
<Accordion title="rollout status times out">
The new pods never became ready. Check `kubectl get pods` and `kubectl logs <pod>`. The old pods keep serving traffic in the meantime, so you can fix the problem or run `kubectl rollout undo deployment/web-app-deployment`.
</Accordion>
<Accordion title="Browser shows 'This site can't be reached'">
Wait two or three minutes for the new load balancer, and make sure you used `http://` and port 80.
</Accordion>
</Accordions>

## Try It Yourself

1. Run the complete pipeline and open the app through the load balancer DNS name.
2. Run it again and watch `kubectl get pods -w` on the EKS home server. Notice the new pods (new hash in their names) replacing the old ones.
3. Change `replicas: 2` to `3`, run the pipeline, and confirm a third pod appears.
4. Change the image tag in the manifest to one that does not exist, run the pipeline, and see `rollout status` fail the build while the old pods keep serving.
5. Delete the Service and Deployment with kubectl and check in the EC2 console that the load balancer disappears.
