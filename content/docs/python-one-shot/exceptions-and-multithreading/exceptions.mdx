Every program so far was written for the good case. The numbers were correct, the input was what the code expected, and the program ran to its last line.

Real users do not behave like that. When you use an app, you expect it to work and you expect it not to crash. If a calculator app crashes, you are annoyed, you open it again and type the numbers once more. The lesson then points at software you cannot see: the software in a car, in a plane, in an MRI machine, in a bank. These are critical. Things will go wrong there too, and the software must keep working when they do.

The things that go wrong while a program runs are called **exceptions**, and a careful program **handles** them. The lesson starts with the kinds of errors a program can have, and then handles one kind step by step.

## Three kinds of errors

The lesson opens an older file, `fact_recursion.py` from [Recursion](/docs/python-one-shot/arrays-and-recursion/recursion), and breaks it in three ways.

```python title="fact_recursion.py"
def fact(num):

    if num == 1:
        return 1

    return num * fact(num - 1)


result = fact(5)
print(result)
```

```text
120
```

### Compile-time error

Change `def` to `deff`. The editor marks the file with red lines at once. This is a mistake in the **syntax**, the grammar of the language. The video only shows the red lines. If you run the file, Python reports the error like this:

{/* check: error */}
```python title="fact_recursion.py"
deff fact(num):

    if num == 1:
        return 1

    return num * fact(num - 1)


result = fact(5)
print(result)
```

{/* check: skip */}
```text
  File "C:\PythonCourse\FirstProject\basics\fact_recursion.py", line 1
    deff fact(num):
         ^^^^
SyntaxError: invalid syntax
```

The instructor calls this the easiest kind of error. You see it while you type, and Python refuses to start the program until it is fixed.

<Callout type="info" title="Compile time in Python">
Python reads the whole file and checks its syntax before it runs the first line. That check is what the lesson calls compile time. A syntax error anywhere in the file means that no line of it runs.
</Callout>

The instructor also types the word `pas` inside the `if`, a `pass` with a missing letter. The editor shows only a yellow warning: `"pas" is not defined`. For Python, `pas` is a valid name that nobody has defined, so the syntax check passes. The error comes when that line runs. Running the file for these docs ended with `NameError: name 'pas' is not defined`. So this one belongs to the third kind below.

### Logical error

Put `def` back and change `return 1` to `return 2`:

```python title="fact_recursion.py"
def fact(num):

    if num == 1:
        return 2

    return num * fact(num - 1)


result = fact(5)
print(result)
```

```text
240
```

No red lines, no error message, and a wrong answer. The factorial of 5 is 120. This is a **logical error**. The syntax is fine and the thinking is wrong.

The lesson calls this kind tricky. Here you know that 120 is expected. Often you do not know the expected answer. If a program fetches the employee with ID 5 from a database and shows the name "Navin", you may be happy to see a name, even when the right one was "Harsh". This is why developers test their code, and why testing teams test it again before it goes to users.

### Run-time error

The third kind appears only while the program runs, and often the developer did nothing wrong. Two examples from the lesson:

- The program divides two numbers that the user types, and the user types zero as the second one.
- The program needs a file on the C drive. It worked for a few days. One day the user frees some disk space and deletes that file.

In both cases the code is correct and the program still stops. These run-time errors are the **exceptions**.

| Kind | When it shows | Example in the lesson | Who notices |
| --- | --- | --- | --- |
| Compile-time (syntax) error | Before the program starts | `deff` for `def` | The editor and Python |
| Logical error | Never by itself, the output is wrong | `return 2` gives 240 | Testing |
| Run-time error (exception) | While the program runs | Division by zero | The user, unless the code handles it |

## Step 1: A program that works

Create a folder `adv` and in it a file `exception_demo.py`:

```python title="exception_demo.py"
a = 5
b = 2

result = a / b
print("Result is:", result)

print("End of program")
```

```text
Result is: 2.5
End of program
```

Run it from the `adv` folder with `python exception_demo.py`. The last line stands for everything a real program still has to do after the division.

## Step 2: Divide by zero

Set `b` to zero. The lesson also changes the last message to "End of execution".

{/* check: error */}
```python title="exception_demo.py"
a = 5
b = 0

result = a / b
print("Result is:", result)

print("End of execution")
```

{/* check: skip */}
```text
Traceback (most recent call last):
  File "C:\PythonCourse\FirstProject\adv\exception_demo.py", line 4, in <module>
    result = a / b
             ~~^~~
ZeroDivisionError: division by zero
```

Read the report from the bottom:

| Part | Meaning |
| --- | --- |
| `ZeroDivisionError` | The type of the exception |
| `division by zero` | The message that belongs to it |
| `line 4` and `result = a / b` | Where it happened |
| `~~^~~` | The marker under the operation. The `/` itself is fine. The trouble is that `b` is 0 |

One line is missing from the output: "End of execution". The program stopped at the division and never reached the last line. That is what a crash is.

The files in the video begin with an empty line, so the video shows `line 5` here. The code on this page starts on line 1, so every line number is one lower than on screen.
</Callout>

## Step 3: try and except

The instructor explains the idea with his son in a restaurant. In a closed restaurant inside a mall, a child who leaves the table is no reason to panic. In an open restaurant next to a highway, the same thing is critical, and the father jumps up at once.

Statements are like that too. `a = 5` and `b = 0` are normal statements. Nothing can go wrong in them. The division is a **critical statement**. Put critical statements in a `try` block:

```python
try:
    result = a / b
    print("Result is:", result)
```

`try` means: try to run these lines, and if one of them fails, the failure will be handled. A `try` alone is not complete. The editor complains at once. If you run the file in that state, Python says `SyntaxError: expected 'except' or 'finally' block`. The handling goes into an `except` block, which also names the kind of error it handles:

```python title="exception_demo.py"
a = 5
b = 0

try:
    result = a / b
    print("Result is:", result)
except Exception:
    print("An error occurred: Division by zero is not allowed.")

print("End of execution")
```

```text
An error occurred: Division by zero is not allowed.
End of execution
```

The division fails. Python leaves the `try` block at that line, so `print("Result is:", result)` is skipped. Then the `except` block runs, and the program goes on after it. "End of execution" is printed. The program did not crash.

An `except` block may do more than print. It could ask the user for a new value of `b` and try the division again.

## The exception hierarchy

Why `Exception`, when the error was a `ZeroDivisionError`? The lesson opens the [exception hierarchy](https://docs.python.org/3/builtins/exceptions.html#exception-hierarchy) in the Python documentation. Exceptions are classes, and they inherit from each other, as you saw in [Inheritance and MRO](/docs/python-one-shot/object-oriented-python/inheritance-and-mro). A small part of the tree:

```text
BaseException
 └── Exception
      ├── ArithmeticError
      │    ├── FloatingPointError
      │    ├── OverflowError
      │    └── ZeroDivisionError
      ├── OSError
      │    └── FileNotFoundError
      ├── RuntimeError
      │    └── RecursionError
      └── ValueError
```

`ZeroDivisionError` is a subclass of `ArithmeticError`, which is a subclass of `Exception`. An `except` block handles the class it names and all its subclasses. So `except Exception` handles a division by zero, a missing file and a wrong value alike. You can ask Python to confirm the family tree:

```python
>>> issubclass(ZeroDivisionError, ArithmeticError)
True
>>> issubclass(ArithmeticError, Exception)
True
>>> issubclass(ValueError, Exception)
True
```

## Step 4: Take the numbers from the user

Fixed values never surprise anyone. Read the two numbers with `input`, as in [User Input](/docs/python-one-shot/functions-modules-and-input/user-input):

{/* check: stdin=4|t; error */}
```python title="exception_demo.py"
a = int(input("Enter numerator: "))
b = int(input("Enter denominator: "))

try:
    result = a / b
    print("Result is:", result)
except Exception:
    print("An error occurred: Division by zero is not allowed.")

print("End of execution")
```

With 4 and 2 the program prints `Result is: 2.0`. With 4 and 0 it prints the message from the `except` block. Then the instructor wants to type 5 and hits the letter `t`:

{/* check: skip */}
```text
Enter numerator: 4
Enter denominator: t
Traceback (most recent call last):
  File "C:\PythonCourse\FirstProject\adv\exception_demo.py", line 2, in <module>
    b = int(input("Enter denominator: "))
ValueError: invalid literal for int() with base 10: 't'
```

A crash again, and no "End of execution". This time it is a `ValueError`: `int()` cannot turn the text `'t'` into a number. The line that failed is outside the `try` block, so nothing handled it. The input lines are critical statements too.

## Step 5: Move the input into the try block

{/* check: stdin=4|t; noout */}
```python title="exception_demo.py"
try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
    print("Result is:", result)
except Exception:
    print("An error occurred: Division by zero is not allowed.")

print("End of execution")
```

{/* check: skip */}
```text
Enter numerator: 4
Enter denominator: t
An error occurred: Division by zero is not allowed.
End of execution
```

No crash. But read the message. Nobody divided by zero. There is one `except` block with one fixed text, and it runs for every kind of error.

## Step 6: Look at the exception object

An exception is an object, and `as` gives it a name. Change the last two lines of the `except` part:

```python
except Exception as e:
    print("An error occurred: Division by zero is not allowed.", e)
```

Printing `e` shows the message of the exception. With 4 and `t`:

```text
Enter numerator: 4
Enter denominator: t
An error occurred: Division by zero is not allowed. invalid literal for int() with base 10: 't'
End of execution
```

And with 4 and 0:

```text
Enter numerator: 4
Enter denominator: 0
An error occurred: Division by zero is not allowed. division by zero
End of execution
```

The second half of the line is now true in both runs. The first half is still the same fixed text.

## Step 7: One except block for each kind of error

The instructor compares this with the days before a board exam at his school. With a maths doubt you went to the maths teacher, with a science doubt to the science teacher. With anything else, a lost hall pass for example, you went to the class teacher.

{/* check: stdin=4|t; noout */}
```python title="exception_demo.py"
try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
    print("Result is:", result)

except ZeroDivisionError as zde:
    print("An error occurred: Division by zero is not allowed.", zde)
except ValueError as ve:
    print("An error occurred: Invalid input. Please enter numeric values only.", ve)
except Exception as e:
    print("An unexpected error occurred:", e)

print("End of execution")
```

{/* check: skip */}
```text
Enter numerator: 4
Enter denominator: t
An error occurred: Invalid input. Please enter numeric values only. invalid literal for int() with base 10: 't'
End of execution
```

With 4 and 0 the first block answers:

```text
Enter numerator: 4
Enter denominator: 0
An error occurred: Division by zero is not allowed. division by zero
End of execution
```

Only one `except` block runs: the first one, from the top, that matches the exception. The last block, `except Exception`, is the class teacher. It is there for safety, for anything the first two do not cover.

## Step 8: finally, the block that always runs

Larger programs open files, database connections and network connections. These are called **resources**, and a program that opens a resource must close it. This program has no real resource, so the lesson pretends with two messages. The closing message goes into a `finally` block:

{/* check: stdin=3|4; noout */}
```python title="exception_demo.py"
print("Resource opened successfully.")

try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
    print("Result is:", result)

except ZeroDivisionError as zde:
    print("An error occurred: Division by zero is not allowed.", zde)
except ValueError as ve:
    print("An error occurred: Invalid input. Please enter numeric values only.", ve)
except Exception as e:
    print("An unexpected error occurred:", e)

finally:
    print("Resource closed.")

print("End of execution")
```

{/* check: skip */}
```text
Resource opened successfully.
Enter numerator: 3
Enter denominator: 4
Result is: 0.75
Resource closed.
End of execution
```

With 4 and 0 there is an exception, and the resource is closed all the same:

```text
Resource opened successfully.
Enter numerator: 4
Enter denominator: 0
An error occurred: Division by zero is not allowed. division by zero
Resource closed.
End of execution
```

| Block | Runs when |
| --- | --- |
| `try` | Always starts. Stops at the first line that raises an exception |
| `except` | Only when an exception of its kind was raised in the `try` block |
| `finally` | Always, with or without an exception |

Now the hard test. The instructor deletes the `ValueError` and `Exception` blocks and types `t`, so that nothing handles the error:

{/* check: stdin=4|t; error */}
```python title="exception_demo.py"
print("Resource opened successfully.")

try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
    print("Result is:", result)

except ZeroDivisionError as zde:
    print("An error occurred: Division by zero is not allowed.", zde)


finally:
    print("Resource closed.")

print("End of execution")
```

{/* check: skip */}
```text
Resource opened successfully.
Enter numerator: 4
Enter denominator: t
Resource closed.
Traceback (most recent call last):
  File "C:\PythonCourse\FirstProject\adv\exception_demo.py", line 5, in <module>
    b = int(input("Enter denominator: "))

```

The program crashes, and "End of execution" is missing. But "Resource closed." is there, before the traceback. The `finally` block ran before the program stopped. That is why clean-up code belongs in `finally`.

### try with finally only

A `try` needs at least one `except` block or a `finally` block. It may have both. The last version in the lesson has `finally` only:

{/* check: stdin=3|4; noout */}
```python title="exception_demo.py"
print("Resource opened successfully.")

try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
    print("Result is:", result)

finally:
    print("Cleaning up resources...")

print("End of execution")
```

The video does not run this version. Run for these docs with 3 and 4, it gives:

{/* check: skip */}
```text
Resource opened successfully.
Enter numerator: 3
Enter denominator: 4
Result is: 0.75
Cleaning up resources...
End of execution
```

With 4 and 0 it prints "Cleaning up resources..." and then stops with the `ZeroDivisionError` traceback. A `finally` block cleans up. It does not handle the exception.

## Additions beyond the lesson

**The else block.** The lesson uses `try`, `except` and `finally`. A `try` statement can also have an `else` block, placed after the `except` blocks and before `finally`. It runs only when the `try` block raised no exception:

{/* check: stdin=3|4; noout */}
```python title="else_demo.py"
try:
    a = int(input("Enter numerator: "))
    b = int(input("Enter denominator: "))
    result = a / b
except ZeroDivisionError as zde:
    print("An error occurred: Division by zero is not allowed.", zde)
else:
    print("Result is:", result)
finally:
    print("Resource closed.")
```

{/* check: skip */}
```text
Enter numerator: 3
Enter denominator: 4
Result is: 0.75
Resource closed.
```

With 4 and 0 the `except` block runs and the `else` block is skipped.

**Specific blocks first.** Python checks the `except` blocks from top to bottom. If `except Exception` stood first, it would match a `ZeroDivisionError` too, and the specific blocks below it would never run. Keep the general block last, as the lesson does.

**What Exception does not cover.** The lesson says `Exception` can handle everything. It handles every ordinary error. A few classes sit beside it, directly under `BaseException`, for example `KeyboardInterrupt`, which is raised when you press Ctrl+C. `except Exception` lets those pass, so you can still stop your program.

## Mistakes and fixes

| What you see | Cause | Fix |
| --- | --- | --- |
| `SyntaxError: invalid syntax` at `deff fact(num):` | A misspelled keyword. This happens in the lesson, on purpose | Write `def` |
| `NameError: name 'pas' is not defined` | `pas` is read as a name. The lesson types it on purpose and the editor only warns | Write `pass`, or remove the line |
| The output is `240` and 120 was expected | A logical error, `return 2` for `return 1`. This happens in the lesson, on purpose | Test with values whose answer you know, then correct the logic |
| `ZeroDivisionError: division by zero` | The denominator is 0 and the division is not in a `try` block | Put the division in `try` and add `except ZeroDivisionError` |
| `SyntaxError: expected 'except' or 'finally' block` | A `try` block with nothing after it. In the lesson the editor marks this while typing, and the file is not run in that state | Add an `except` block, a `finally` block, or both |
| `ValueError: invalid literal for int() with base 10: 't'` | The user typed a letter, and the `input` lines were outside the `try` block. This happens in the lesson | Move the `input` lines into the `try` block and add `except ValueError` |
| "Division by zero is not allowed." for the input `t` | One general `except` block with a fixed message. This happens in the lesson | Print the exception with `as e`, or write one `except` block for each kind |
| "End of execution" is not printed | An exception that no `except` block matched stopped the program | Handle that kind of exception, or add `except Exception` as the last block |

<Callout type="info" title="A slip of the tongue">
While reading the `ValueError`, the instructor says that the `input` function tried to convert the text. `input` only returns the text. The conversion is done by `int()`, as the message itself says: `invalid literal for int()`.
</Callout>
