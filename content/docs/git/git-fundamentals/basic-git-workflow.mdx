After installing and configuring Git, the next step is understanding how Git manages changes to your project.

Every change you make in Git follows a simple workflow:

```text
Working Directory → Staging Area → Local Repository (Commit History)
```

Once you understand this flow, using Git becomes much easier because almost every Git command interacts with one of these three areas.



## Understanding Git's Three Stages

Git doesn't immediately save every change you make. Instead, it moves changes through three stages before they become a permanent part of your project's history.

![Git_Workflow_Stages](https://dyz1pdcuffwr5.cloudfront.net/Git/git_workflow_stage.png)

Let's understand each stage in detail.

### 1. Working Directory

The **Working Directory** is the project folder where you actively write and modify your code.

Every action you perform starts here, such as:

- Creating new files
- Editing existing files
- Deleting files
- Renaming files

At this stage, Git knows that changes exist, but they are **not yet prepared for a commit**.

**Example**

Suppose your project contains:

```text
Calculator/
├── index.html
├── style.css
└── script.js
```

If you modify `script.js`, the change exists only in the **Working Directory** until you explicitly tell Git to track it.


### 2. Staging Area

The **Staging Area** (also called the **Index**) is a temporary holding area where you choose which changes should be included in the next commit.

Instead of committing every change immediately, Git lets you review and organize them before creating a snapshot.

You move changes into the staging area using:

```bash
git add
```

**Why is the Staging Area useful?**

Imagine you've made two changes:

- Fixed a bug
- Added a new feature

You may want to commit only the bug fix first and save the feature for later.

The staging area allows you to decide exactly what goes into each commit.


### 3. Local Repository (Commit History)

The **Local Repository** stores the complete history of your project.

When you commit your staged changes, Git creates a permanent snapshot of the project.

```bash
git commit
```

Each commit becomes a version that you can:

- Revisit
- Compare
- Restore
- Share with other developers

Think of each commit as a checkpoint in your project's timeline.

## How Git Identifies Changes?

One of Git's biggest strengths is that it can precisely detect changes in your project.

It does this using **checksums**, which are generated using the **SHA-1 hashing algorithm**.

Whenever you create a commit, Git generates a unique **40-character hexadecimal hash**.
* Git's checksum changes whenever the contents of a commit change.
* Even modifying a single character in a file produces a completely different checksum.

Example:

```text
fd914d5319d3aeb39c14c4f7da6501dd666b3ea3
```

Since the full hash is long, Git usually displays only the first seven characters:

```text
fd914d5
```

These first seven characters are normally enough to uniquely identify a commit.

## Creating a Git Repository

Before Git can track your project, you need to initialize a repository.

### Initialize a New Repository

```bash
git init
```

This command creates a hidden `.git` folder inside your project.

Example:

```text
MyProject/
├── .git/
├── index.html
└── app.js
```

The `.git` directory contains:

- Commit history
- Branch information
- Configuration
- Metadata
- Object database

Without this folder, Git cannot track your project.

Example output:

```text
Initialized empty Git repository in /project/.git/
```


### Initialize with a Custom Default Branch

Modern repositories usually use **main** as the default branch.

Instead of creating `master`, you can directly initialize with:

```bash
git init -b main
```

This creates the repository with **main** as the initial branch.


### Checking Repository Status

One of the most frequently used Git commands is:

```bash
git status
```

It shows the current state of your repository.

Specifically, it tells you:

- Which files are modified
- Which files are staged
- Which files are untracked
- Whether your working directory is clean

Example:

```text
modified: app.js

Untracked files:
notes.txt
```

Many developers run `git status` before every commit to verify exactly what will be committed.

## Add Files and Create Commit

### Adding Files to the Staging Area

Before Git can create a commit, the desired changes must be staged.

**Stage a Specific File**

```bash
git add <filename>
```

Example:

```bash
git add app.js
```

Only `app.js` is added to the staging area.

**Stage All Files**

```bash
git add .
```

This stages every new and modified file inside the current directory.

Use this command when you're ready to commit all your changes together.


### Creating a Commit

Once your changes are staged, save them permanently using:

```bash
git commit -m "your message"
```

Example:

```bash
git commit -m "Add login functionality"
```

The `-m` option lets you provide a meaningful commit message describing what changed.

Good commit messages make it much easier to understand your project's history.


### Viewing Commit History

To see all commits in a repository, use:

```bash
git log
```

Git displays information such as:

- Commit hash
- Author
- Date
- Commit message

Example:

```text
commit fd914d5...

Author: John Doe

Date: Mon Aug 3

Add login feature
```

This allows you to review the complete history of your project.


### Skipping the Staging Step

Normally, Git requires two commands:

```text
git add
git commit
```

For **already tracked files**, Git provides a shortcut:

```bash
git commit -a -m "your message"
```

Example:

```bash
git commit -a -m "Fix navigation bug"
```

The `-a` option automatically stages **modified tracked files** before creating the commit.

**Important Limitation**

This command **does not stage new files**.

For newly created files, you must still use:

```bash
git add
```

before committing.

</Step>

## Viewing Changes with Git Diff

Git allows you to compare changes before committing them.

### View Unstaged Changes

```bash
git diff
```

Shows the difference between:

- Working Directory
- Staging Area

Use it to review modifications that haven't been staged yet.


### View Staged Changes

```bash
git diff --staged
```

Shows the difference between:

- Staging Area
- Last Commit

This lets you verify exactly what will be included in your next commit.

### Understanding File Status

Git assigns different states to files depending on where they are in the workflow.

| Status | Meaning |
|---------|---------|
| **U (Untracked)** | Git has never tracked this file before. |
| **M (Modified)** | The file has changed since the last commit. |
| **A (Added)** | The file is staged and ready to be committed. |

Understanding these states makes it easier to interpret the output of `git status`.

</Step>

## Removing a File from Git Tracking

Sometimes you want Git to stop tracking a file but keep it on your computer.

For example:

- `.env`
- Configuration files
- Secret keys
- Local settings

Use:

```bash
git rm --cached <filename>
```

Example:

```bash
git rm --cached .env
```

This command:

- Removes the file from Git tracking
- Keeps the file on your local system
- Marks the file as untracked

This is commonly used before adding files to `.gitignore`.

> **Note:** Deleting a file from your project folder does not automatically remove it from Git's tracking history. If you want Git to stop tracking a file while keeping it locally, use `git rm --cached`.

</Step>

## Quick Reference

| Command | Purpose |
|---------|---------|
| `git init` | Initialize a new Git repository |
| `git init -b main` | Initialize a repository with `main` as the default branch |
| `git status` | Display the current state of the repository |
| `git add <file>` | Stage a specific file |
| `git add .` | Stage all new and modified files |
| `git commit -m "message"` | Create a commit with a descriptive message |
| `git commit -a -m "message"` | Automatically stage modified tracked files and commit them |
| `git log` | View the complete commit history |
| `git diff` | Show unstaged changes |
| `git diff --staged` | Show staged changes before committing |
| `git rm --cached <file>` | Stop tracking a file while keeping it on the local system |
