Everything is ready. Four commands take the app live. Replace `telusko-content-tracker` with **your** project ID in every command.

## Step 1: Enable the services

```bash
gcloud services enable run.googleapis.com artifactregistry.googleapis.com cloudbuild.googleapis.com
```

| API | What it does for us |
| --- | --- |
| Cloud Run | Runs our container and serves it over HTTPS |
| Artifact Registry | Stores our Docker image |
| Cloud Build | Builds the image in Google Cloud from our source |

This takes a minute and ends with `Operation finished successfully`.

## Step 2: Create an Artifact Registry repository

```bash
gcloud artifacts repositories create telusko-repo \
  --repository-format=docker \
  --location=us-central1 \
  --description="Docker images for the Telusko Workflow Engine"
```

`us-central1` is the region. Pick one close to your users, and use the **same region** in every following command.

## Step 3: Build and push the image with Cloud Build

From the project root (where the `Dockerfile` is):

```bash
gcloud builds submit \
  --tag us-central1-docker.pkg.dev/telusko-content-tracker/telusko-repo/telusko-app:latest
```

The image path has a fixed structure:

```text
us-central1-docker.pkg.dev / telusko-content-tracker / telusko-repo / telusko-app:latest
└──── region + registry ───┘ └──── project ID ──────┘ └── repo ───┘ └── image:tag ──┘
```

Cloud Build uploads your project, runs the Dockerfile in Google Cloud, and pushes the finished image to the repository. You see the same steps as your local build in the logs.

## Step 4: Deploy to Cloud Run

First, generate a **strong** secret in your own terminal:

```bash
python -c "import secrets; print(secrets.token_hex(32))"
```

Then deploy:

<Tabs items={["macOS / Linux", "Windows (PowerShell)"]}>
<Tab value="macOS / Linux">

```bash
gcloud run deploy telusko-app \
  --image us-central1-docker.pkg.dev/telusko-content-tracker/telusko-repo/telusko-app:latest \
  --platform managed \
  --region us-central1 \
  --allow-unauthenticated \
  --port 8080 \
  --set-env-vars "JWT_SECRET_KEY=<your-generated-secret>,JWT_ALGORITHM=HS256,JWT_ACCESS_TOKEN_EXPIRE_MINUTES=60"
```

</Tab>
<Tab value="Windows (PowerShell)">

```powershell
gcloud run deploy telusko-app `
  --image us-central1-docker.pkg.dev/telusko-content-tracker/telusko-repo/telusko-app:latest `
  --platform managed `
  --region us-central1 `
  --allow-unauthenticated `
  --port 8080 `
  --set-env-vars "JWT_SECRET_KEY=<your-generated-secret>,JWT_ALGORITHM=HS256,JWT_ACCESS_TOKEN_EXPIRE_MINUTES=60"
```

</Tab>
</Tabs>

| Flag | Meaning |
| --- | --- |
| `telusko-app` | Name of the Cloud Run service |
| `--image` | The image we just pushed |
| `--region` | Same region as the repository |
| `--allow-unauthenticated` | Anyone can open the URL. Our app has its own login, so that is what we want |
| `--port 8080` | The port the container listens on |
| `--set-env-vars` | The JWT settings, as comma-separated `NAME=value` pairs |

<Callout type="warn" title="Watch the quotes">
In the video, the first attempt failed because of a missing closing double quote around `--set-env-vars`. If the shell waits for more input or `gcloud` complains about arguments, check your quotes first.
</Callout>

When it finishes, `gcloud` prints the **Service URL**, something like `https://telusko-app-xxxxxxxxxx.us-central1.run.app`, and shows that the new revision serves 100% of traffic.

## Step 5: Test the live app

Open the Service URL. Cloud Run gives you **HTTPS** automatically.

| Test | Expected |
| --- | --- |
| Open the URL | Login page |
| `admin` / `admin123` | Full board, delete available |
| `editor` / `editor123` | Can move cards from Recorded and Editing only, cannot move back, no delete |
| Logout | Back to the login page |

## Before you call it production

What we deployed is a great learning result. A few things deserve attention before real users rely on it:

<Callout type="warn" title="SQLite on Cloud Run is not persistent">
Our SQLite database file lives **inside the container**. Cloud Run containers are disposable: when an instance restarts, scales down to zero or a new revision is deployed, the file is recreated from scratch, and the seed script loads the demo data again. With several instances, each one even has its own separate database. For real data, move to a managed database such as [Cloud SQL for PostgreSQL](https://cloud.google.com/sql/docs/postgres) (remember the worktree decision notes in Section 7: this is exactly the trade-off we recorded).
</Callout>

- **Secrets:** `--set-env-vars` is fine for learning. For production, store the JWT secret in [Secret Manager](https://cloud.google.com/run/docs/configuring/services/secrets) and reference it from Cloud Run
- **Demo users:** remove or change the seeded accounts and their simple passwords
- **CORS:** with a single origin, the old localhost CORS entries are no longer needed
- **Costs:** if you were only experimenting, delete the service when you are done:

```bash
gcloud run services delete telusko-app --region us-central1
```
